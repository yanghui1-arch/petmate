# 项目git规范
## 分支
一个分支意味着一个更新任务，做完这个任务就提交pr，pr合并后没有问题就删除这个分支
例如：现在有一个任务是 移除所有无用代码
1. 首先创建一个本地分支 `git checkout -b remove/useless-codes`
2. 其次创建一个远程分支 `git push -u origin remove/useless-codes`
3. 写完更新代码后，提交PR，由审核A来合并PR，PR合并后若无问题，则删除该分支即可

### 分支提交流程的最佳实践
1. 当有一个新的需要解决的问题的时候，开发者会`git checkout -b feature/branch`创建一个新的分支，然后在这个分支上进行开发，此时分支的内容是基于创建时所处的最新的分支内容
2. 随着开发者在自己的分支上进行开发了一段时间后，原来基于的分支可能发生了变动，而这些变动没有被合并到开发者自己的分支
3. 开发者最后提交自己分支之前，需要主动合并一次原来基于的分支，以此合并原来基于的分支的变动`git merge origin/main` 如果遇到冲突，请手动解决好冲突再提交PR

## 不接受的提交
对现有代码侵入性太强，如改动千行/目录结构发生太大变化。此类提交必须带有详细说明，必要时需要提交完整的测试代码和测试结果

## 推荐的提交
1. 原子性提交，根据下面的提交信息，一次提交只做一件事，如`[fix]`就只做修复bug一件事，不可以再做`[style]`的事情
2. 代码侵入式较低，普遍而言一次提交最好控制在代码改动 `<=` 200行
3. 附有详细的说明和测试用例代码

## 合并
改动超过400行以上的提交，需要至少通过3个人的代码审查

## 提交信息
所有提交的信息都应当为 "[] ", 其中 应当使用中文且简明扼要, 参考如下:

- feat: 新增 feature, 新增功能时常用
- fix: 修复 bug
- remove: 移除 代码，通常是无用代码
- docs: 仅仅修改了文档, 比如 README
- style: 修改代码风格，但未改变代码逻辑
- refactor: 代码重构, 没有加新功能或者修复 bug
- perf: 优化相关, 比如提升性能
- test: 测试用例, 包括单元测试或集成测试等
- chore: 改变构建流程, 或者增加依赖库及工具等, 比如修改 pom.xml
- revert: 回滚到上一个版本
- replace: 替换某个内容
