# Spec Coding 工作流程

本项目按功能维护规格文档，遵循“先写 spec，再做计划，最后实现”的顺序。本文约定工作流程，不代表具体功能的需求或实现方案已经获得批准。

## 目录约定

功能目录使用三位编号和英文名称，例如 `001-farm`。以下为文档组织示例，各文件只在对应阶段创建：

```text
spec/
  README.md
  001-farm/
    spec.md
    plan.md
    tasks.md
```

- `spec.md`：描述要解决的问题、功能范围、用户操作、业务规则、异常情况及可验证的验收标准；记录明确不做的事项和待澄清问题。
- `plan.md`：在 spec 确认后编写，记录代码现状、至少 3 种可行方案及其优缺点、适用场景和主要权衡；用户选择方案后完善实现步骤、数据设计、影响范围和验证方式。
- `tasks.md`：在计划批准后编写，将已批准方案拆为可执行、可验证的任务，并跟踪完成情况。

## 执行顺序与确认节点

1. **澄清需求**：信息不完整或存在多种理解时，先询问用户；需求明确前不自行假定功能行为。
2. **编写 spec**：获得文档写入授权后创建 `spec.md`，明确范围、规则和验收标准。待澄清问题必须得到解决，才能进入下一阶段。
3. **确认 spec**：用户明确确认规格后，才开始编写计划。规格确认仅批准需求，不等同于批准代码实施。
4. **编写计划并选择方案**：分析现有实现，提供至少 3 种可行方案供用户选择；选择后补全 `plan.md`，使实施内容和验证方式可审查。
5. **批准计划**：用户明确批准完整计划并要求开始实施后，才进入实现阶段；文档或目录创建授权不等同于代码修改授权。
6. **拆分任务并实现**：创建 `tasks.md`，按已批准方案完成任务，及时更新进度。
7. **验证与验收**：按 spec 验收标准和计划验证功能，记录实际验证结果及尚未解决的问题；未验证的事项不得标记为通过。

## 变更规则

- 未获得相应授权时保持只读，可以阅读、分析和提出建议，不执行文件创建、修改、删除或其他写入操作。
- 需求范围或业务规则发生变化时，先更新 spec 并获得确认，再调整计划；涉及新的代码实施方案时，重新获得批准。
- 文档使用“草稿、待确认、已确认”等明确状态，并在进入下一阶段前记录用户确认结果。
- 不提前创建计划、任务或实现代码，不将未确认的设想当作既定需求。
- spec、计划和任务记录纳入版本控制；提交操作遵循用户授权。
