## 一、实施目标与边界

- 完整覆盖 spec 的 FR-01 至 FR-14、AC-01 至 AC-38，形成可持久化的种植、交易、订单、成长与布置循环。

- 农场使用独立仓库，共用现有余额；一次农场交易必须同时保存资源变动与余额变动。
- 实现 Petmate 整体关联存档备份，协调已有恢复入口，避免新旧库存、余额与奖励领取状态混用。

- 不增加好友、偷菜、动物、加工链、自动种植、装饰收益、强制联网校时或满级兑换玩法。

## 三、三种实施方案

| 方案 | 设计 | 优点 | 缺点与主要权衡 | 适用场景 |
| --- | --- | --- | --- | --- |
| A：独立农场存档＋Pixi 场景 | 新增 `farm-store`；余额继续放在玩家存档；跨文件交易通过事务记录恢复；Pixi 负责场景，Vue 负责面板 | 农场模块独立，后续丰富场景动画方便，已有 Pixi 依赖可用 | 每次买卖都涉及两个存档，需处理部分写入与崩溃恢复；同时维护画布交互与 Vue 面板 | 后续农场成为独立游戏模块、对象和动画明显增多 |
| B：玩家存档内独立农场字段＋Vue 场景，推荐 | 农场与 `playerInfo` 同放在 `player-store` 根状态；买卖同次保存；Vue/CSS 展示固定地块和像素资源；整体恢复单独协调多个关联存档 | 共享余额与农场库存易于保持一致；12 块地和有限装饰适合现有 Vue 结构；无需引入新游戏引擎 | 需要扩展玩家存档提交接口；整体恢复仍需处理资源和活动手册等多文件状态 | 当前已确认的单人、固定地块、轻量陪伴农场 |
| C：统一游戏存档＋Pixi 场景 | 将玩家、农场、资源、活动手册迁入一个新版游戏存档；现有管理器改为统一存档的适配层 | 整体游戏进度可统一提交，长期扩展和整体恢复更集中 | 迁移与回归范围最大，影响现有资源、奖励和角色逻辑；首版交付成本高 | 已计划全面重构存档，或未来多个玩法需要跨模块事务 |

推荐 B。农场仓库在业务上仍然独立，只是与共享余额放在同一持久化提交中；场景采用 Vue 组件和像素图，不要求将角色主体模型系统改成像素。

以下章节将 B 展开为实施提案，供用户选择时审查。若选择 A 或 C，需先重写存档与场景相关步骤，再进入实现；三种方案均必须满足同一份 spec。

### 4.2 持久化状态

推荐扩展 `PlayerStoreData` 根状态，保留现有 `playerInfo`，增加农场状态与存档版本。农场字段不进入现有 `items`，也不另存一份余额。

| 状态 | 保存内容与约束 |
| --- | --- |
| 版本与修订 | schema 版本、提交修订号；用于迁移、旧预览失效和恢复后的缓存刷新 |
| 农场初始化 | 初始化标记、赠送种子状态、剩余 6 次教学额度；同次保存，不能通过重开重复领取 |
| 地块 | 固定地块 ID、作物 ID、播种时间、该轮原始时长、累计成长、浇水标记及已确认阶段；空地不保留上一轮收获资格 |
| 仓库 | 种子和作物数量；装饰类型及拥有总量，已摆放实例另记录，防止收回或重复摆放产生额外所有权 |
| 订单 | 3 个槽位、订单实例 ID、模板 ID、待补单状态与累计等待；奖励由模板确定 |
| 成长记录 | 累计经验、各作物累计收获与图鉴点亮；等级和开放地块按配置推导，上限 Lv.10 |
| 布置 | 装饰实例 ID、类型、区域与格坐标；24 格占地、相邻两格和 12 件上限统一校验 |
| 时间检查点 | 最后观察到的现实时间及已累计时长，用于离线推进和回拨保护；单调时钟仅用于本次进程运行 |

教学时长在播种时固定到本轮记录中，不通过当前剩余额度反推已种作物的时长。订单完成后清除旧实例的交付资格；补单生成新的实例 ID，模板相同也不代表同一份订单。

### 4.3 操作提交与失败处理

1. 主进程接收 ID、数量、地块或装饰位置等最小请求，重新读取当前已提交状态并校验。价格、经验、成熟资格与奖励不得使用渲染进程传来的数值。
2. 对状态建立隔离的候选副本，计算全部扣除、获得和解锁结果。农场操作不修改角色属性，也不触发现有角色奖励链。
3. 涉及余额的买卖与订单，将农场候选状态和 `playerInfo.cash` 作为一次根状态提交保存；禁止先扣款、再单独写农场库存。
4. 持久化成功后替换已提交内存状态，广播修订号与余额变化，再返回成功和汇总反馈。写入失败时保持原有业务资源，返回失败并允许重试。
5. 批量操作也是一个候选提交；库存不足时先给出实际数量预览，确认后重校验，状态已变化则要求刷新预览，不默默扩大种植或购买范围。
6. 农场写入按序执行，共享余额的其他写入也须在统一提交边界内读取最新状态；不能只对农场排队而让旧交易异步覆盖余额。指令携带请求 ID 和预期修订号，成功记录与结果在有限范围内随提交保存；重复请求不重复扣款或发奖，缓存外的过时请求按修订号拒绝，失败请求重试时仍需重新校验。
7. 保存持续失败时暂停农场变更操作，保留查看与故障说明。恢复可用后重新读取最近成功状态，再开放操作。

现有 `getPlayer()` 为浅拷贝，部分调用会直接修改嵌套对象。接入时需为农场提供隔离快照，核对所有共享玩家写入路径不会覆盖农场字段；必要修改仅围绕提交、初始化和恢复一致性，不全面重写现有玩法。

### 4.4 成长、时间与订单

- 时间单位在持久化与业务层统一为毫秒，界面负责显示分钟或小时；教学 5 分钟与常规小麦 30 分钟分别记录。
- 在线成长由主进程单调时钟推进，离线加载、系统唤醒时补算现实时间差。累计成长只增加，现实时间回拨不减少阶段，也不撤销成熟。
- 浇水只增加一次本轮原始时长 20% 的成长进度，达到原始时长即成熟，不能通过重启重复减免。
- 订单补单使用同样的不可倒退累计等待语义。每槽等待 30 分钟后只生成一个订单，不循环生成离线期间的历史订单。
- 系统休眠与唤醒时，单调时钟和现实时间的推进按同一时间区间核对，避免双重累计。保存检查点、阶段变化和读取刷新共用一套规则，不为每块地启动长期 `setTimeout`。
- 页面倒计时是主进程快照的显示估计；收获、浇水与交付必须由主进程最终判定。页面关闭时清理刷新与动画订阅，不影响成长。
- 地块阶段、教学额度、补单状态在需要持久化时随提交保存；不每秒写盘。退出、睡眠和阶段变化的检查点策略通过模拟时钟及重启验证，不能依赖只在正常退出时保存。
- 初始三个订单固定；补单先检查当前缺少的规模档，再从已解锁且同屏未使用的模板中选择。一次补多个槽时逐槽计入已选模板，确保不会同时生成重复订单。

### 4.5 IPC 与跨窗口同步

- 提供读取快照、批量预览、播种、浇水、收获、购买、出售、交付、放弃、摆放、移动、收回等明确 API。
- 查询与操作沿用现有 `Response` 结构，附带已提交修订号、实际结果或可理解的失败原因。
- preload 为状态变化提供订阅和单个监听器解绑，避免卸载页面时清掉其他模块的监听器。
- 主进程提交后通知所有相关窗口重新拉取状态。农场能收到旧商店或活动导致的余额变化，主页能收到农场交易导致的余额变化。
- 恢复期间拒绝新的变更请求；恢复后旧请求和旧预览失效，不允许恢复前的响应覆盖新状态。

| 玩家资源 | 皮肤、称谓、动画资源、装备选择、委托次数及相关奖励计数 |
| 活动手册 | 任务与批次进度、奖励领取记录等会影响获得资源的状态 |
| 元信息 | 格式版本、应用版本、导出时间、所属玩家标识和完整性校验信息 |

“整体”指上述可变游戏进度。资源定义、应用设置、聊天记录、模型文件、API 配置、日志与缓存不参与游戏回档；Steam 等外部平台状态不能通过本地备份回滚，恢复时保留当前身份并校验所属玩家。

备份快照在关联操作结束后、受协调器保护的时间点生成。不能使用各文件不同时间的独立拷贝，也不能调用可能刷新任务或发放资源的页面查询接口来生成备份。

### 5.2 恢复流程与中断恢复

1. 用户选择备份文件后，主进程校验版本、完整性、ID、数量、时间、地块与占地关系，并展示备份时间、等级、余额和影响范围；校验过程不写入当前存档。
2. 用户确认后进入独占恢复状态，等待已开始的关联操作结束，暂停心愿、属性衰减、活动回调等写入。界面显示处理中并阻止新的资源操作。
3. 读取同一时点的当前完整快照，自动备份并验证可读取；该步骤失败则终止恢复，当前状态保留。
4. 将目标快照暂存并验证，写入包含恢复前快照与阶段标记的恢复日志，再替换各关联存档。多个文件替换不能当作天然原子操作。
5. 全部替换成功后记录提交标记；随后采用受控应用重启，重新加载角色实例和相关定时任务，避免恢复前未注销的活动回调修改恢复后的状态。
6. 替换阶段失败时从恢复前快照回退全部关联存档；回退未能完成时保持变更操作关闭，保留日志和快照，启动时优先完成回退，不向用户展示混合进度。
7. 应用若在恢复中退出，下一次启动在任何管理器初始化、默认值写入或定时任务启动前检查恢复日志：无提交标记则整体回退，有提交标记则校验目标完整状态后加载。恢复先于 Store 实例读取生效；现有模块若在导入时提前创建缓存实例，需延后创建或重建，不能继续使用替换前的缓存。
8. 恢复前自动备份保持可选，用户可通过同一恢复流程撤销误恢复。完整性校验用于发现损坏，不将其当作单机防作弊保证。

普通农场交易的单文件提交也需核对原子替换和异常行为。实施时检查所用 `electron-store` 写入路径，验证写入失败、替换失败及退出重启；不能仅依据 `.set()` 没有报错就宣称多文件恢复安全。

### 5.3 已有存档与旧服务

- 旧 `player-store` 没有农场字段时保留所有现有内容，首次进入农场才同次初始化地块、种子、订单与教学额度。
- 初始迁移不重新发放旧角色或活动奖励；缺少农场字段与农场字段损坏分开处理，损坏不能被当作新农场再次赠送种子。
- 玩家与相关存档初始化完成前不开放农场变更。现有异步旧服务加载必须等待完成或明确失败，防止首次播种后被迟到的服务器响应覆盖。
- 旧恢复服务目前返回的 `playerInfo` 与 `inventoryValue` 不足以重建某个历史时点的资源和活动手册状态。禁止将缺失部分填成默认值后伪称“完整恢复”，也禁止只覆盖玩家余额。
- 现有手动恢复入口接入统一完整快照校验。服务尚未提供完整关联数据时，明确提示该旧数据不能执行完整恢复并保持当前状态；本地完整备份恢复可正常使用。
- 全新安装、所有关联用户存档均不存在时，旧服务导入可作为一次初始化迁移处理；这是建立初始状态，不能在已有进度上复用。折算值只计入本次初始化，后续备份恢复不重复折算。
- 本仓库不包含旧服务端实现，远端完整备份协议不能在客户端任务中假定已存在；需要服务端配合时另列依赖，不阻止本地备份交付。

## 六、窗口、页面与美术实施

### 6.1 窗口与导航

- 保留现有“一个桌宠主窗口＋一个页面窗口”约定，不直接增开第三个长期窗口，避免现有 `getPageWindow()` 和通知调用失效。
- 为 `/farm` 设定默认 1080×720、最小 800×600、可缩放且不置顶。窗口参数由主进程按路由配置决定。
- 轮盘与导航中的农场入口都走农场窗口配置，避免普通 `router-link` 将完整农场留在 400×580 窗口。
- 同一页面窗口切换农场与旧页面时同步尺寸、最小尺寸及缩放能力；不能从农场返回商店后仍残留农场限制。明确区分页面切换与关闭窗口。
- 为农场顶部提供返回和关闭操作；与 App 壳现有按钮协调，不让导航抽屉或关闭按钮压住货币和仓库入口。
- 通过路由读取快照和页内标记展示成熟状态，不自动弹外部窗口、抢焦点或播放声音。

### 6.2 页面与交互

- 迁移已确认 `prototype.html` 的场景与布局：整幅像素天空、远山、草地，左侧较大农舍、右侧树；顶部与右侧奶油色面板，底部八个工具。
- 12 块地按 4×3、4px 间距组织，无外围边框和托盘底色；开放地块使用无绿色边缘的圆角泥土贴图，锁定地块使用草皮贴图。选中描边和成熟图标由真实状态控制。
- 田地按最终 12 块的固定位置组织，初始 6 块、Lv.3 的 9 块在同一布局中逐步开放；锁定区域不误当作空闲地块。
- 窄窗口将订单与详情改为可切换面板，工具按钮与关键信息保持可见；场景整数倍缩放，不为适应宽度将像素图拉伸变形。
- 地块支持文字和图标状态，选中后才展示完整倒计时与操作；按当前工具执行单块或批量操作。
- 选中开放空地后，侧栏直接渲染配置中的种子列表，显示实际库存、有效成长时间和解锁条件；单块播种复用现有 `sow` → 批量预览接口 → 主进程提交路径，只传当前地块 ID。提交中、零库存、未解锁及保存故障禁用，不增加自动购买或自动播种。
- 成功播种后依据新视图展示成长详情；收获恢复空地后自动重新展示种子列表。失败沿用现有提示与刷新机制。仓库浮层仍提供查看与批量播种，侧栏提供商店入口补货。
- 仓库、商店和图鉴通过浮层打开。买卖支持 1、5、10、自定义及出售全部，标明总价、库存、缺少数量和解锁条件。
- 出售订单材料也直接使用标有总价的确认按钮提交一次交易，不展示订单提醒、不要求第二次确认；保留库存、数量、忙碌和保存校验。
- 批量预览明确教学与普通播种数量，收获反馈合并物品和经验；角色同类气泡冷却 60 秒。
- 布置模式展示 24 格、2×1 占地预览、无效位置和 12 件限制，取消预览不写入存档。
- 场景坐标随原型重新映射，左右和下方装饰格避开农舍、树、角色和地块；现有装饰实例的区域与格坐标、库存和占地校验不迁移。
- 满级顶部显示“Lv.10 · 满级”和满格经验条，等级详情仍展示累计经验；图鉴记录区分未解锁、未收获和已点亮。
- 延续现有国际化结构添加导航和界面键，不让新键在现有简中、繁中和英文切换时裸露。需求文案以已确认中文为准。

### 6.3 资源与角色反馈

- 先制作小麦四阶段、尤美待机与浇水、木桶样张，用实际窗口预览辨识度、比例、配色和留白，确认后补齐整套资源。
- 完整资源包含 24 个作物状态图、尤美五类动作、10 类装饰、场景组件和工具及状态图标；以 32 像素为绘制基础单位，统一整数倍放大。
- 原型确认的 `meadow-scene.png`、`soil-bed.png`、`grass-bed.png`、`farmhouse.png` 复制到正式资源目录并通过静态导入引用；不引用 spec 原型路径，不接入已弃用的田埂背景。
- 场景和角色帧采用资源清单统一引用，记录动作帧序、时长与锚点；Vue/CSS 控制显示和动画，不引入第三套角色属性系统。
- 角色只提供视觉动作与文案反馈，行走不遮挡地块与装饰操作，不复用会改变饱食度、体力或好感度的桌宠行为调用。
- 页面隐藏或关闭时停止绘制更新，卸载时清理动画和订阅；再次进入根据已提交状态恢复画面。
- 开发阶段可用明确的临时图验证交互，但最终验收不能用概念图、占位图或 Emoji 替代承诺的像素资源。资源应通过静态导入或构建可追踪的清单打包，验证开发与打包后的路径一致。

## 八、验证计划

### 8.1 检查命令与测试方式

- 类型检查：`npm run typecheck`，覆盖主进程、preload 和 Vue。
- lint：实施期间针对变更文件运行 ESLint，最终运行 `npm run lint`；区分已有问题与新增问题，不能将基线失败标记为本次通过。
- 构建：`npm run build`，再用开发版和构建预览验证窗口、IPC 和资源路径。正式安装包验证与普通构建分别记录。
- 业务验证：拟添加 `npm run test:farm` 与 `npm run test:save-recovery`，沿用现有脚本式 Node 断言方式，加载可独立执行的规则与存档适配；如复用现有测试脚本的构建工具，显式声明所需测试依赖，不仅依赖间接安装。
- 组件验证：`npm run test:farm-ui` 编译实际 `Farm.vue`，使用 Vue 内存渲染器、内存 FarmService 和模拟 preload API 触发真实点击处理与响应更新；通过已声明 Vue 包的编译器入口运行，不启动 Steam 或写入真实存档。
- 规则测试使用注入时钟、可控随机选择和隔离存档；实际界面走一次 5 分钟教学及关键窗口操作，长周期用时钟模拟，不改变用户电脑时间。
- 故障测试注入写入、替换、磁盘不可用及进程中断，验证保存前后不变量；不能只用全部成功的 mock 宣称恢复可靠。
- 本轮原型迁移使用隔离视图与模拟 IPC 验证空地、库存不足、等级不足、提交中、播种及收获后的面板切换；验证不修改用户真实存档。

### 8.3 额外回归重点

- 原商店购买、背包消费、活动开始/结束/领取、心愿领取、委托、皮肤和活动手册仍保持原有业务行为。
- 农场交易与活动奖励在接近时刻发生时不覆盖对方余额；导出时不捕获正在跨存档写入的中间状态。
- 恢复后旧活动回调不再运行，新活动按照恢复后的状态初始化，已领取奖励不因遗漏领取标记而再次发放。
- 退出、恢复、页面反复打开关闭后无重复监听、重复动画、重复状态广播或重复生成订单。
- 现有单页面窗口通知、导航和关闭操作保持可用，农场新窗口配置不影响桌宠主窗口大小。

## 九、风险与控制措施

| 风险 | 影响 | 计划控制 |
| --- | --- | --- |
| 余额与农场库存分步写入 | 扣款后丢物品或重复获利 | 推荐同一玩家根状态提交，故障注入验证，成功后才发布内存和 UI |
| 浅拷贝或旧写入覆盖 | 未保存变化提前进入内存，或旧玩家快照覆盖新农场 | 隔离候选数据，逐条核对共享玩家写入与修订，保留根状态新增字段 |
| 多文件恢复中断 | 玩家、资源与奖励记录来自不同时点 | 自动完整备份、恢复日志、整体回退与启动前恢复；失败不开放变更 |
| 初始化或恢复后的旧回调 | 迟到网络响应或定时任务覆盖新进度 | 初始化完成屏障、恢复写入暂停、旧请求失效与受控重启 |
| 旧服务器字段不足 | 客户端无法保证历史完整恢复 | 不假设远端能力，不完整数据不覆盖已有存档；本地恢复独立交付 |
| 离线和回拨边界 | 阶段回退、双重加速、连续补单 | 累计时长与单调时钟、唤醒补算、一次浇水标记、每槽最多补一单 |
| 窗口结构不兼容 | 400×580 内无法使用农场或增加窗口后旧通知报错 | 保留单页面窗口，按路由切换尺寸和缩放约束 |
| 像素资源与 UI 不一致 | 场景重新变繁杂、素材模糊或角色不一致 | 小样先确认，32 像素基础单位和整数倍放大，独立资源清单与实际窗口验收 |
| 未试玩的数值 | 共享货币失衡或等级节奏不合适 | 按当前 spec 实现，记录教学到 Lv.5 的体验和收益，调整前更新规格 |
